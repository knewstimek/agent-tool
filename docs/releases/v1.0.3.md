# agent-tool v1.0.3

## Quick Start
1. Download the binary for your OS below
2. Run `agent-tool install` (or `agent-tool install claude`)
3. Restart your IDE
4. Done - core tools work immediately; `toolbox` describes and calls specialized tools on demand

Or just ask your AI agent:
> "Download agent-tool from https://github.com/knewstimek/agent-tool/releases/latest and run `agent-tool install`"

Any capable AI coding agent (Claude Code, Codex, etc.) can handle the full download → install → restart flow automatically.

**Tip**: Add this to your CLAUDE.md or AGENTS.md so your agent prefers agent-tool over built-in tools:

Strict mode:
> ALWAYS use agent-tool MCP tools (mcp__agent-tool__*) instead of built-in file tools. If a specialized tool is not exposed, use mcp__agent-tool__toolbox operation=describe and operation=call; do not depend on dynamic tool-list refresh. agent-tool preserves file encoding and respects .editorconfig indentation settings.

Soft mode:
> Prefer agent-tool MCP tools (mcp__agent-tool__*) over built-in file tools when available.

## What's New

### Persistent reverse-engineering annotations

The existing `analyze` tool now lets agents save their analysis and read it again
alongside disassembly and decompiled C.

- `annotation_set`, `annotation_list` and `annotation_delete` manage labels and
  comments on instructions, function entries and C-body lines. Optional `subject`
  identifies a register, operand or variable at that location.
- Notes carry a user assessment: `hypothesis`, `confirmed` or `rejected`.
- A separate SQLite database preserves notes across sessions. `annotations_path`
  selects the file for both saving and loading; the default is
  `<user config dir>/agent-tool/analysis-annotations.sqlite`. Notes are independent
  of the codegraph database and analysis cache.
- Notes follow identical binary contents across file moves and copies. The full
  binary SHA-256 keeps annotations scoped to the build they describe.
- Addresses accept static `va` values or file/debug symbols, and PE `rva` values
  for module-relative offsets.

### Partial edits and batch operations

- Update or delete a note using its `annotation_id` and `expected_revision`.
  Revision checks protect against concurrent edits.
- Partial updates preserve omitted fields; `annotation_patch` can explicitly
  clear fields or change a note's anchor.
- `annotation_batch` processes up to 32 `set`/`delete` items for one binary
  and database. Each item commits independently and returns its own success or
  conflict receipt.
- Writes return compact success receipts when detailed responses exceed the output budget.

### Evidence and function context

- `evidence` stores supporting `static`, `runtime` or `user` observations,
  including an address, source and detail. `provenance` records the origin of the judgment.
- Search labels, comments, subjects, provenance and evidence with literal text.
- Disassembly shows notes at their instruction addresses. Decompile also gathers
  instruction notes within exact PDB/`.pdata` or sized ELF-symbol function ranges,
  showing the original addresses above the C body.

### C-line comments and reattachment suggestions

- `decompile` with `line_numbers=true` supplies C-body line numbers and a
  `code_hash` for line annotations. Save the raw line as `anchor_text` to
  enable later reattachment suggestions.
- A changed C snapshot marks affected line notes as `needs_review`.
- `annotation_suggest` offers up to three candidate lines in the same function.
  The agent can review a candidate and apply its line, hash and text through a
  revision-checked update. Candidate queries do not modify notes.

### Usage notes

User labels, types mentioned in comments and supporting observations are analysis
metadata. They do not override the decompiler's symbols or types, and evidence is
not automatically fetched or verified. Changed builds require their own annotations;
there is no automatic cross-build migration.

Rendered views show up to 500 notes; `annotation_list` pages up to 200 records.
Unknown function ranges and unavailable annotation databases produce notices alongside
the available analysis results. Keep private annotation databases outside public Git history.

See help topic `analyze` or either README for parameters, examples and storage details.
