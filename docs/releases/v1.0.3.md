# agent-tool v1.0.3

## Quick Start
1. Download the binary for your OS below
2. Run `agent-tool install` (or `agent-tool install claude`)
3. Restart your IDE
4. Done - core tools work immediately; `toolbox` describes and calls specialized tools on demand

Or just ask your AI agent:
> "Download agent-tool from https://github.com/knewstimek/agent-tool/releases/latest and run `agent-tool install`"

Any capable AI coding agent (Claude Code, Codex, etc.) can handle the full download → install → restart flow automatically.

**Tip**: Add this to your CLAUDE.md or AGENTS.md so your agent prefers agent-tool over built-in tools:

Strict mode:
> ALWAYS use agent-tool MCP tools (mcp__agent-tool__*) instead of built-in file tools. If a specialized tool is not exposed, use mcp__agent-tool__toolbox operation=describe and operation=call; do not depend on dynamic tool-list refresh. agent-tool preserves file encoding and respects .editorconfig indentation settings.

Soft mode:
> Prefer agent-tool MCP tools (mcp__agent-tool__*) over built-in file tools when available.

## What's New

Keep reverse-engineering knowledge alongside the code you are analyzing. The existing
`analyze` tool now saves user labels, comments and supporting observations, then shows
them again in disassembly and decompiled C. No additional MCP tool is needed.

### Persistent labels and comments

- `annotation_set`, `annotation_list` and `annotation_delete` manage notes on
  instructions, function entries and C-body lines. Optional `subject` identifies a
  register, operand or variable at that location.
- `annotation_status` records `hypothesis`, `confirmed` or `rejected`. Displayed
  user notes remain separate from automatic symbols and debug types.
- A separate SQLite database stores the notes. `annotations_path` manually selects
  the file for both saving and loading; relative paths follow the workspace/MCP root.
  The default is `<user config dir>/agent-tool/analysis-annotations.sqlite`.
  Notes are independent of the rebuildable codegraph DB and disposable analysis cache.
  Reads do not create databases.
- The full binary SHA-256 scopes notes: moving or copying identical bytes preserves
  access to them; changed binaries do not inherit another build's annotations.
  Addresses and IDs remain exact strings. Use static `va` (hex or a file/debug
  symbol), or PE `rva` for a module-relative offset.

### Safe partial edits and batches

- Read a note's ID and string revision, then pass `annotation_id` and
  `expected_revision` to update or delete it. Stale requests are rejected.
  Creating an already occupied anchor cannot bypass the revision guard.
- Updates preserve omitted fields. `annotation_patch` supports explicit clearing
  with empty text, an empty evidence array, or `line=0` when changing anchor kind.
- `annotation_batch` handles up to 32 `set`/`delete` items sharing one binary
  and database, with one database open and binary hash. Each item commits independently
  and returns an indexed success or conflict receipt; one failure does not undo
  successful items.
- Output budgets are checked before writes. When full details cannot fit, successful
  writes still return a short JSON receipt with the ID/revision instead of an
  output-size error. Batches require at least `768 * item_count + 256` characters.

### Evidence and function context

- Optional `evidence` records supporting `static`, `runtime` or `user`
  observations, with an address, source and detail. `provenance` records the origin
  of the judgment. These are user-supplied assertions; sources are not fetched or
  automatically verified.
- Literal searches cover comments, labels, subjects, provenance and decoded evidence,
  including `<`, `>`, `&`, quotes and backslashes.
- Decompile gathers interior instruction notes from exact PDB/`.pdata` or sized ELF
  symbol ranges and shows their original addresses above the C body. Unknown or
  limited ranges produce a notice; notes are not guessed onto individual C lines.
  Range loading reads exact metadata without repeating whole-binary call-graph analysis.
- If an annotation database cannot be loaded, disassembly and decompilation still
  return their analysis results with a visible warning.

### C-line comments and reviewed reattachment

- `decompile` with `line_numbers=true` returns C-body L numbers and a
  `code_hash`. Save a line note with that hash, its function entry and line number;
  include the raw line as `anchor_text` for later suggestions.
- A changed C snapshot keeps the comment as `needs_review` rather than attaching it
  to an unrelated line.
- `annotation_suggest` returns the current hash/revision and up to three candidate
  lines from stored text or token overlap. Equal top scores are marked ambiguous;
  missing or generic anchors may require manual selection.
- Suggestions never modify the database. After reviewing a candidate, apply a
  revision-checked patch containing its `line`, `code_hash` and `anchor_text`.

### Compatibility and limits

- The analyze operation set grows from 24 to 29; tool descriptions, compact discovery,
  help and both READMEs describe the new operations.
- Labels, subjects and evidence are metadata, not decompiler symbol/type overrides.
  There is no automatic cross-build annotation migration.
- Rendered views show at most 500 notes; `annotation_list` pages up to 200 records.
  Function summaries use at most 16 exact ranges per function.
- Annotation schema v3 reads pre-release v1/v2 databases without modifying them and
  migrates missing fields atomically on the first write, preserving notes and revisions.
  Older pre-release builds that only understand v1/v2 cannot open a v3 database.
- Keep private annotation databases outside public Git history. The default filename
  and `*.annotations.sqlite*` are ignored by this repository; custom names need
  their own ignore rule.
