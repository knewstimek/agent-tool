# agent-tool v1.0.0

## Quick Start
1. Download the binary for your OS below
2. Run `agent-tool install` (or `agent-tool install claude`)
3. Restart your IDE
4. Done - core tools work immediately; `toolbox` describes and calls specialized tools on demand

Or just ask your AI agent:
> "Download agent-tool from https://github.com/knewstimek/agent-tool/releases/latest and run `agent-tool install`"

Any capable AI coding agent (Claude Code, Codex, etc.) can handle the full download → install → restart flow automatically.

**Tip**: Add this to your CLAUDE.md or AGENTS.md so your agent prefers agent-tool over built-in tools:

Strict mode:
> ALWAYS use agent-tool MCP tools (mcp__agent-tool__*) instead of built-in file tools. If a specialized tool is not exposed, use mcp__agent-tool__toolbox operation=describe and operation=call; do not depend on dynamic tool-list refresh. agent-tool preserves file encoding and respects .editorconfig indentation settings.

Soft mode:
> Prefer agent-tool MCP tools (mcp__agent-tool__*) over built-in file tools when available.

## What's New

agent-tool 1.0 adds a decompiler. `analyze(operation="decompile")` turns x86/x64 PE and ELF
functions into C using [Gosleigh](https://github.com/knewstimek/gosleigh), a Go port of Ghidra's
decompiler core, with debug information from PDB and DWARF applied the way Ghidra's analyzers do.
No Ghidra, Java, or external process is required.

### Decompiler

- `analyze(operation="decompile", path=..., va=...)`: `va` takes a hex address or a function name,
  up to 16 functions per call. Embedded Ghidra x86/x64 language specs; Visual Studio conventions
  for PE, gcc for ELF, and Ghidra's golang spec for Go-built binaries (register ABI parameters).
- Host knowledge from the file: function starts (.pdata, exports, symbols, call targets, entry
  point), import names, read-only sections, and tail calls rendered as `return f();`.
- **PDB** (found through the image's RSDS record and used only when the GUID matches;
  `pdb_path` overrides it, `pdb_path="none"` disables it): qualified names, prototypes, `this`,
  struct/class/union/enum types, typed globals and vftables, MSVC-demangled public names, and
  local variables with names and types (x64 frames located from unwind codes, RBP frames from
  `UWOP_SET_FPREG`).
- **DWARF** (ELF, MinGW and Go PE images): names, prototypes, types, globals and stack locals.
- Bitfield members print as fields (`p->ready = 0;`, `p->bFlag == 0`) instead of masks.
- Go 386 (ABI0) results are read back from their stack slot.
- Non-returning functions are detected like Ghidra's analyzers (known-name lists, debug-info
  flags, call-site discovery), and their call sites get CALL_RETURN overrides.
- The PDB is also used by `function_at` (exact bounds and names, x86 included), `disassemble`,
  `call_graph`, `instruction_search`, `follow_ptr` and `struct_layout`.

### Isolation and performance

- Each decompile runs in a worker process (the same executable) with a 2 GB heap watchdog,
  `timeout_sec` (default 60, max 600) and client-cancel handling. Workers die with the server
  (Windows kill-on-close job object, Linux parent-death signal, parent watch everywhere).
- Workers stay loaded between calls on the same binary (at most 2 idle, retired after 2 minutes):
  on a 78 MB x64 image with its PDB, later calls take 0.1-0.2 s.
- Whole-binary scans are cached under the user cache directory (`agent-tool/analysis`, 256
  entries, keyed by file identity and the agent-tool executable; `AGENT_TOOL_NO_ANALYSIS_CACHE=1`
  disables it). A first load of that image in a new session takes about 0.7 s instead of 3.3 s.
- `AGENT_TOOL_ANALYZE_THREADS` bounds scan goroutines; the default is NumCPU/4 clamped to 2-4.
- Faster import-name and export reads speed up `disassemble`, `call_graph` and
  `instruction_search` on large binaries.

### Corpus command

- `agent-tool decompile-all <binary> -o out.jsonl` writes every known function as one JSON line
  (`{entry,name,c,secs}` or `{entry,error}`) on `-j` pooled workers, with a per-function
  `-timeout`, `-pdb`, `-limit` and resume of an existing output file. Largest functions are
  scheduled first; output lines are in completion order.

### SSH

- `ssh` accepts `powershell_script` (UTF-8, up to 4 MiB), staged through a temporary file over
  SSH stdin, so long scripts work on legacy Windows servers without SFTP. Long standalone
  `-EncodedCommand` invocations are staged automatically; temporary scripts are cleaned up, and a
  failed cleanup is reported as `cleanup_warning`.
- Local SSH/SFTP profiles default to `trusted:true`: the private-address warning is shown once
  per pooled connection. SSRF blocking and cloud metadata protection are unchanged.

## Verification

- Measured against 400 Ghidra 12 golden functions from two real MSVC executables: all 400
  decompiled without engine errors, and tail-call overrides matched Ghidra on all 125 jumps.
  Mean token similarity to Ghidra is 0.90 on the x86 sample and 0.80 on the x64 sample with its
  PDB (0.48 without debug information).
- MCP end-to-end checks cover PE/ELF x86/x64, PDB auto-detection, GUID mismatch,
  `pdb_path="none"`, analyze names, input errors, worker reuse, timeout kill and orphan cleanup.

## Dependencies and size

- New: `github.com/knewstimek/gosleigh` v0.1.5 (Apache-2.0, includes Ghidra's specs) and
  `github.com/knewstimek/gopdb` v0.1.2 (MIT, PDB reader and MSVC demangler).
- The Windows binary grows by about 7 MB (decompiler engine, embedded specs, PDB and DWARF).

## Compatibility

- No breaking MCP tool names or startup changes. `agent-tool __decompile-worker` is an internal
  subcommand, not a user command.

## Known limits

- x86/x64 only (other architectures are rejected with a `disassemble` hint); Mach-O and
  OMAP-reordered PE images are not supported.
- Go functions with several results show only the first.
- The first call on a large binary pays the load (about 0.7-3 s for a 78 MB image with its PDB).
